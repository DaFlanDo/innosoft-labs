# InnoSoft Labs — Описание системы

> Документ актуален на 2026-03-14. Основан на анализе исходного кода.

---

## 1. Назначение системы

**InnoSoft Labs** — корпоративная система управления проектами и задачами (Project Management Tool) для команды разработчиков. Система предназначена для:

- Организации работы небольшой команды (5–20 человек) над несколькими параллельными проектами
- Постановки задач, отслеживания их выполнения и приоритизации
- Контроля доступа к проектам через систему ролей
- Хранения файловых вложений к задачам
- Приглашения новых участников в проекты через одноразовые ссылки
- Аналитики по команде и проектам

**Что система НЕ является:** это не таск-трекер уровня Jira/Asana с agile-спринтами, не система управления договорами или финансами, не CRM.

## 3. Сущности и их смысл

### 3.1 Пользователи (`users`)

Каждый пользователь системы. Поля:
- `name`, `email`, `password_hash` — стандартная аутентификация
- `initials` — отображаются в аватаре если нет фото (например "АК")
- `role` — текстовое поле, должность ("Frontend Разработчик", "Руководитель проектов"). **Важно:** от значения этого поля зависят глобальные права доступа

**Глобальные администраторы** — пользователи, у которых в поле `role` встречается одно из слов: `руководитель`, `manager`, `admin`, `менеджер`, `администратор`. Только они могут создавать и удалять проекты.

### 3.2 Проекты (`projects`)

Верхнеуровневая единица работы. Каждый проект:
- Имеет `статус`: `planning → active → review → completed → archived`
- Имеет `приоритет`: `low / medium / high`
- Имеет `цвет` (#HEX) для визуальной идентификации
- Имеет `deadline` — крайний срок всего проекта
- Имеет `progress` (0–100%) — процент выполнения (вычисляется на фронтенде как доля задач в статусе `done`)
- Принадлежит `owner` — пользователю-создателю

### 3.3 Участники проектов (`project_members`)

Связь M2M: каждый пользователь может участвовать в нескольких проектах с разными ролями:

| Роль | Права |
|------|-------|
| `owner` | Все права + удаление проекта |
| `manager` | Управление участниками, создание/изменение/удаление задач, приглашения |
| `member` | Создание задач, комментирование, загрузка файлов |
| `viewer` | Только просмотр |

### 3.4 Задачи (`tasks`)

Основная рабочая единица. Задача:
- Принадлежит проекту (`project_id`)
- Имеет `статус`: `todo → progress → done` (три колонки канбан-доски)
- Имеет `приоритет`: `low / medium / high`
- Имеет `assignee` — назначенный исполнитель (один)
- Имеет `due_date` — срок выполнения
- Имеет `теги` (произвольные строки: "Frontend", "Design", "Backend" и т.д.)

### 3.5 Комментарии (`comments`)

Обсуждение в рамках конкретной задачи. Только текст.

### 3.6 Вложения (`task_attachments`)

Файлы, прикреплённые к задаче. Физически хранятся в MinIO (S3-совместимое хранилище). В БД хранится метаинформация + URL файла.

### 3.7 Уведомления (`notifications`)

Системные уведомления пользователю (например, "вас добавили в проект", "задача изменена"). Поле `type` — строка-идентификатор типа события, `message` — текст.

### 3.8 Приглашения (`invitations`)

Одноразовые или многоразовые ссылки для вступления в проект:
- Создаются менеджером/владельцем проекта
- Имеют `token` — случайная строка в URL
- Могут быть ограничены по количеству использований (`max_uses`) и сроку действия (`expires_at`)
- При переходе по ссылке — незарегистрированный пользователь может сразу зарегистрироваться и вступить в проект
- Зарегистрированный пользователь принимает приглашение через `/api/invite/{token}/accept`

## 4. Сценарии использования

### 4.1 Вход в систему
1. Пользователь открывает браузер → `/login`
2. Вводит email + пароль → POST `/api/auth/login`
3. Получает JWT-токен (срок 7 дней), сохраняется в `localStorage`
4. При каждом запросе токен передаётся в заголовке `Authorization: Bearer <token>`

### 4.2 Просмотр рабочего пространства
1. Дашборд — сводная статистика (всего проектов, задач, выполненных, в процессе)
2. Последние 3 проекта и 6 задач

### 4.3 Работа с проектами
1. Администратор создаёт проект (название, описание, приоритет, цвет, дедлайн)
2. Администратор или менеджер добавляет участников вручную или через invite-ссылку
3. На странице "Проекты" — сетка карточек. Клик по карточке открывает детальное представление
4. В детальном представлении: задачи проекта, список участников, управление приглашениями

### 4.4 Работа с задачами
1. Канбан-доска — три колонки: "К выполнению", "В процессе", "Готово"
2. Drag & drop между колонками меняет статус задачи (PATCH `/api/tasks/{id}`)
3. Фильтрация задач по проекту
4. Клик по карточке — детальное представление: изменение всех полей, комментарии, вложения
5. Вкладка "Мои задачи" — задачи, назначенные на текущего пользователя

### 4.5 Приглашение участников
1. Менеджер проекта в деталях проекта создаёт invite-ссылку с указанием роли
2. Копирует URL вида `https://app.example.com/login?invite=TOKEN`
3. Получатель переходит по ссылке → если не авторизован, видит форму регистрации/входа с предзаполненными данными о проекте
4. После аутентификации — автоматически добавляется в проект с указанной ролью

### 4.6 Аналитика
- Страница аналитики показывает:
  - Сводные цифры по системе
  - Количество задач по каждому проекту (бар-чарт)
  - Распределение задач по статусам (пай-чарт)
  - Прогресс по проектам
  - Топ участников по выполненным задачам
- Данные кэшируются в Redis на 5 минут, кэш сбрасывается при изменениях

### 4.7 Реалтайм-обновления
- При открытии страницы задач фронтенд подключается к WebSocket-комнате проекта
- События `task:created`, `task:updated`, `task:deleted`, `project:updated` обновляют состояние без перезагрузки
- **Статус реализации:** Subscribe/unsubscribe на фронтенде реализован. Emit с бэкенда в API-роутах **не подключён** (см. раздел 6).

## 5. Поток данных при старте приложения

```
1. App.tsx монтируется
2. Есть токен в localStorage?
   ├─ Да → GET /api/auth/me (проверка валидности)
   │        ├─ Успех → setCurrentUser(user)
   │        │          loadAll() → параллельно:
   │        │            GET /api/projects
   │        │            GET /api/tasks
   │        │            GET /api/users
   │        │          loadNotifications() → GET /api/notifications
   │        └─ Ошибка → удалить токен → редирект /login
   └─ Нет → редирект /login
```

## 6. Несоответствия и проблемы

### 6.1 Критические

| # | Проблема | Расположение | Последствие |
|---|----------|-------------|-------------|
| 1 | **MySQL вместо PostgreSQL** | `docker-compose.yml`, `config.py` | README вводит в заблуждение. Документация разработчика неверна |
| 2 | **SQL-триггеры несовместимы с MySQL** | `backend/sql/triggers.sql` | Файл написан для PostgreSQL (`gen_random_uuid()`, `LANGUAGE plpgsql`). При запуске на MySQL выдаст ошибку. Триггеры никогда не выполнялись |
| 3 | **WebSocket emit не подключён к API** | `backend/app/socket/handlers.py`, все роутеры | Хелперы `emit_task_created/updated/deleted` определены, но не вызываются из роутов `tasks.py` и `projects.py`. Реалтайм не работает |

### 6.2 Архитектурные

| # | Проблема | Расположение | Последствие |
|---|----------|-------------|-------------|
| 4 | **Дубликат схемы MemberOut** | `backend/app/schemas/project.py` | Класс определён дважды, вторая версия скрывает первую. Может привести к неожиданному поведению |
| 5 | **Alembic-миграция неполная** | `backend/alembic/versions/001_initial.py` | Таблицы `task_attachments` и `invitations` не включены в миграцию. При использовании `alembic upgrade head` они не создаются — только через `create_all()` при старте |
| 6 | **Расхождение requirements.txt / pyproject.toml** | корень backend/ | `requirements.txt` → `redis[asyncio]>=5.0.0`, `pyproject.toml` → `aioredis==2.0.1`. Это разные пакеты. Источником истины должен быть один файл |

### 6.3 Функциональные

| # | Проблема | Расположение | Последствие |
|---|----------|-------------|-------------|
| 7 | **Прогресс проекта не обновляется автоматически** | `backend/` | Поле `progress` в таблице `projects` не пересчитывается при изменении статуса задач. Фронтенд вычисляет его локально (`calcProjectProgress`), но в БД всегда 0 после создания |
| 8 | **`GET /api/users` без авторизации** | `backend/app/api/users.py` | Список всех пользователей системы доступен без токена. Это скорее всего непреднамеренно |
| 9 | **Права создания задач игнорируют проект** | `backend/app/api/tasks.py` | `POST /api/tasks` принимает `project_id` в теле, но check на членство в проекте может выполняться нестрого — нужна проверка |
| 10 | **Legacy-код в корне проекта** | `index.html`, `app.js`, `styles.css`, `js/` | Старый Vanilla JS фронтенд занимает место и создаёт путаницу. Никак не используется в production-сборке нового React-приложения |

### 6.4 Нереализованные функции (заглушки)

| Функция | Статус |
|---------|--------|
| Уведомления через WebSocket | Структура есть, emit не вызывается |
| Реалтайм синхронизация задач | Подписка на фронтенде есть, сервер не отправляет |
| Поиск в Header | UI есть, фильтрация только локальная (не API-поиск) |
| Страница "Команда" | Страница есть, компонентов в `components/team/` нет |
| Календарь событий | Только дедлайны проектов, задачи не показываются |
